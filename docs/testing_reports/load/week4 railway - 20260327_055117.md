## Root Cause Analysis — group1_cpu/moderate Burst Failure

**Data sources:**
- Locust stats history CSV (1-second granularity): failure rate peaked at 50.9 failures/s between t=83–88s; zero failures at t=0–73s and t=103–120s
- Honeycomb query (dataset `gatheryourdeals`, environment `test`, window 05:52:40–05:53:10 UTC): all 435 HTTP 401 spans confirmed within the 30-second burst window

**HTTP 401s are user-not-found, not wrong password:**

Honeycomb spans for the 401 responses show **P50 duration = 2.44ms**. A correct-user login with wrong password would invoke `bcrypt.CompareHashAndPassword` (cost 12, ~2,700ms). The 2.44ms response time is sub-DB-roundtrip, meaning `GetUserByUsername` returned `nil` before bcrypt was attempted. The service correctly maps a nil user to `ErrInvalidCredential` → HTTP 401.

The 75 HTTP 500 errors had P99=3,432ms — consistent with bcrypt CPU saturation under 100 concurrent goroutines on a single Railway vCPU.

**Probable cause — transient PgBouncer connection disruption:**

Under heavy bcrypt CPU load (100 concurrent hashing operations each taking ~2.7s), the Railway PgBouncer instance likely briefly recycled or health-checked idle connections. During this ~30-second window, some `GetUserByUsername` queries returned without a result row, causing the 401 cascade. The throughput spike to 64–70 req/s during the burst (vs normal 36 req/s) is consistent with queued requests draining quickly via fast 401 responses rather than 2.7s bcrypt completions.

**Not a code regression:**

Week 3 run (GitHub run `23630392237`, same `develop` branch, same Railway environment, 90 minutes earlier) recorded **0 errors** on `cpu_bound/moderate` with identical throughput (36.1 req/s, avg 2,736ms). The code is byte-for-byte identical.
