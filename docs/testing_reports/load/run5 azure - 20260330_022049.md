# Summary

This article records the load testing results from run #5, the first successful load test run against Azure Container Apps + PostgreSQL Flexible Server via pgBouncer (session mode).

Service was deployed on Azure Container Apps (Consumption plan, `westus3`) backed by Azure PostgreSQL Flexible Server (`gyd-pg-main`) via pgBouncer Container App (`gyd-pgbouncer`).

**4 of 8 phases fully valid; 2 phases had test infrastructure defects; 2 phases produced invalid results.** Both `read_heavy` phases are invalid: moderate suffered a login stampede (400 → 64 users); stress had a 48-second Locust startup overhead that consumed the entire shape budget, so the 90-second hold phase never ran and 2000 users existed for only 1 second. The 82 read timeouts in stress are real (pool saturation during ramp-up) but do not represent steady-state 2000-user load. All other 6 phases passed cleanly, including `write_ops/stress` (500 users, 716 RPS).

> **Post-run investigation (2026-03-30):** Both `read_heavy` phases confirmed invalid. See [Post-Run Investigation](#post-run-investigation) section below.

## Root Cause Analysis — read_heavy/stress

**Hold phase never ran (test infrastructure issue):**

Locust's `get_run_time()` starts from process creation, not from when users begin spawning. The 48-second startup overhead (guardrail, prefetch, initialization) consumed the shape budget before user traffic began. By the time 2000 users were reached (~101s after `test_start`), `get_run_time()` had already hit the 150s limit (`ramp_time=60 + stress_hold=90`), and the shape returned `None`. The 2000-user hold phase lasted 1 second instead of 90 seconds. The 82 failures and low RPS (3 RPS) all occurred during ramp-up, not steady-state load.

**Bimodal latency during ramp-up:**

The P50 is 17–20ms — consistent with a healthy pgBouncer pool serving the requests that acquire a connection. The P95 jumps to 60s. This bimodal pattern is the classic signature of **connection pool queue overflow**: as ramping users exceeded `MAX_CLIENT_CONN=200`, additional requests queued indefinitely and timed out.

**pgBouncer configuration limits (explicitly set in `infra/azure/persistent/container-app.yaml`):**

```
DEFAULT_POOL_SIZE = 50    # backend PostgreSQL connections per pool
MAX_CLIENT_CONN   = 200   # max simultaneous clients pgBouncer accepts
```

In session mode, each connected client holds one backend connection. Once the ramp exceeded 200 users, pgBouncer's client limit was hit; further requests queued. Of the 200 connected clients, only 50 got backend connections immediately — the rest queued. The bottleneck is the explicitly configured pgBouncer limits, not the PostgreSQL server's `max_connections`.

**Low actual RPS (3 RPS vs 500 target):**

At saturation, most requests are queued waiting for connections. Threads are occupied waiting rather than executing, so effective throughput collapses. The low actual RPS is a symptom of the saturation, not an independent issue.

**Fix path:**

Switch pgBouncer from session mode to **transaction mode** (requires `QueryExecModeSimpleProtocol` on the pgx driver). In transaction mode, a backend connection is held only for the duration of a transaction — allowing 50 backend connections to multiplex across all connected clients. `MAX_CLIENT_CONN` can also be raised independently. Additionally, fix the 48-second startup overhead so the hold phase actually runs.

## Post-Run Investigation

**Investigation date:** 2026-03-30

### Findings

After reviewing the artifact from GitHub Run `23725032367`, three anomalies were identified across both `read_heavy` phases.

#### 0. read_heavy/stress: Hold Phase Never Ran (Test Infrastructure Bug)

The `stats_history.csv` shows user count reached 2000 for exactly 1 second then immediately wound down:

```
t=+101s (test_start): 2000 users — peak
t=+102s:              1898 users — shape returned None, wind-down begins
t=+150s:              98 users   — test ends
```

**Root cause:** Locust's `get_run_time()` starts from process creation, not from when users begin spawning. The 48-second startup overhead (guardrail, prefetch, Python init) consumed the shape budget silently. By the time 2000 users were reached at `test_start + 101s`, `get_run_time()` had already reached `ramp_time(60) + stress_hold(90) = 150s`, causing the shape to return `None` immediately.

The intended 90-second hold at 2000 users never happened. The 82 failures and ~3 RPS occurred during ramp-up (when users exceeded `MAX_CLIENT_CONN=200`), not under steady-state 2000-user load. Pool saturation is confirmed real, but its severity at true steady-state is unknown.

**Impact:** The stress results show ramp-up behaviour only. Steady-state 2000-user performance has never been measured.

**Fix:** Account for Locust startup overhead in `run_group.sh` — either pre-warm Locust before starting the shape timer, or increase `GYD_STRESS_HOLD` to compensate for the ~48s offset.

---

After reviewing `read_heavy/moderate` specifically:

#### 1. User Count Collapse: 400 → 64 (Test Infrastructure Bug)

The `stats_history.csv` shows the user count dropped from 400 → 314 → 64 within the first 30 seconds of the test:

```
t=0s:  400 users spawned (spawn_rate=400/sec — all at once)
t=12s: first request completes (830ms response time)
t=30s: 314 users remaining
t=31s: 64 users — stable for remainder of 120s test
```

**Root cause — two compounding issues:**

**Issue A — Per-user login against a single account (design bug):** The seed has one test user account. All 400 `ReadUser` workers call `safe_login()` in `on_start()` with the same credential (`GYD_TEST_USERNAME` / `GYD_TEST_PASSWORD`). This triggers 400 independent bcrypt verifications for the same password. The login endpoint handles ~7.4 bcrypt/sec on this hardware (3.75 vCPUs). Processing all 400 logins requires ~54 seconds; users whose login hasn't completed within the 30-second `login()` timeout hit `StopUser`. This is a test design bug — read workers do not need to authenticate individually and should share a pre-fetched token instead.

**Issue B — Instantaneous spawn rate:** `make_shape()` returns `(400, 400)` for moderate phase — all 400 users spawn within 1 second. This fires all 400 bcrypt logins simultaneously, amplifying the CPU saturation from Issue A. Capping the spawn rate alone is insufficient because the total bcrypt work (400 logins at 7.4 RPS) still exceeds the timeout budget; it only changes the failure shape, not the outcome.

Other groups (cpu_bound=100, write_ops=100, misc_lightweight=110) are unaffected — their smaller spawn counts complete within the 30s timeout window at Azure's bcrypt throughput.

**Why this did not occur on Railway (runs 3–4):** Railway was provisioned with 8 vCPUs, giving ~36 bcrypt/sec login throughput. 400 logins ÷ 36 RPS = ~11 seconds — well within the 30s timeout. The same design bug exists on Railway but is masked by the higher CPU budget. If Railway vCPUs were reduced, the same collapse would occur.

**Impact:** `read_heavy/moderate` ran at 16% of intended capacity (64 of 400 users). Actual RPS was ~12–16 per endpoint; intended was ~100. The results are not representative of 400-user moderate load.

#### 2. P95 Lower Than Average (Statistical Contamination)

For `GET /api/v1/meta` moderate: **Avg=214ms, P50=18ms, P95=21ms**.

This is statistically valid but misleading. The cumulative stats include both:
- **Steady state (64 users, ~90s):** P50=18ms, P95=21ms — clean
- **Stampede window (400 users, ~30s):** a few requests with 9,700–23,180ms response times (P99=9700ms, P99.9=21,000ms, max=23,180ms)

With 1,356 total requests, approximately 14 requests averaging ~12,000ms inflate the cumulative mean from ~18ms to ~214ms. The P95 correctly reflects the 64-user steady state; the mean is contaminated by the stampede window. This pattern repeats across all four `read_heavy/moderate` endpoints.
