# Summary

This article records the load testing results from run #5, the first successful load test run against Azure Container Apps + PostgreSQL Flexible Server via pgBouncer (session mode).

Service was deployed on Azure Container Apps (Consumption plan, `westus3`) backed by Azure PostgreSQL Flexible Server (`gyd-pg-main`) via pgBouncer Container App (`gyd-pgbouncer`).

**6 of 8 phases valid; 1 phase had a test infrastructure defect; 1 phase failed.** The `read_heavy/moderate` phase suffered a login stampede that collapsed users from 400 → 64, making its results invalid (tested at 16% intended capacity). The `read_heavy/stress` phase failed with 82 read timeouts (4.96% error rate) due to pgBouncer connection pool saturation — this result is still valid. All other 6 phases passed cleanly, including `write_ops/stress` (500 users, 716 RPS).

> **Post-run investigation (2026-03-30):** `read_heavy/moderate` numbers are suspicious and confirmed invalid. See [Post-Run Investigation](#post-run-investigation) section below.

## Root Cause Analysis — read_heavy/stress Failure

**Bimodal latency distribution:**

The P50 for all read endpoints is 17–20ms — extremely fast, consistent with a healthy pgBouncer pool. The P95 jumps to 60s (the Locust timeout). This bimodal pattern (fast P50, timeout P95) is the classic signature of **connection pool queue overflow**: requests that acquire a connection immediately complete in ~20ms; requests that queue for more than 60 seconds time out.

**PostgreSQL connection limit:**

Azure PostgreSQL Flexible Server's default `max_connections` varies by SKU. On the Burstable `B1ms` tier (the cheapest tier often provisioned in CI), `max_connections = 50`. pgBouncer in session mode holds one backend connection per active client. With 2000 Locust users all issuing reads, pgBouncer's client pool size can reach hundreds while only 50 backend connections are available — causing the queue overflow.

**Fix path:**

Switch pgBouncer from session mode to **transaction mode** (requires `QueryExecModeSimpleProtocol` on the pgx driver, same as the TODO from run 4). In transaction mode, a backend connection is held only for the duration of a transaction, not the entire client session — allowing the 50 backend connections to serve thousands of concurrent clients without queuing. Alternatively, upsize the PostgreSQL SKU to increase `max_connections`.

## Post-Run Investigation

**Investigation date:** 2026-03-30

### Findings

After reviewing the artifact from GitHub Run `23725032367`, two anomalies were identified in `read_heavy/moderate`:

#### 1. User Count Collapse: 400 → 64 (Test Infrastructure Bug)

The `stats_history.csv` shows the user count dropped from 400 → 314 → 64 within the first 30 seconds of the test:

```
t=0s:  400 users spawned (spawn_rate=400/sec — all at once)
t=12s: first request completes (830ms response time)
t=30s: 314 users remaining
t=31s: 64 users — stable for remainder of 120s test
```

**Root cause — two compounding issues:**

**Issue A — Per-user login against a single account (design bug):** The seed has one test user account. All 400 `ReadUser` workers call `safe_login()` in `on_start()` with the same credential (`GYD_TEST_USERNAME` / `GYD_TEST_PASSWORD`). This triggers 400 independent bcrypt verifications for the same password. The login endpoint handles ~7.4 bcrypt/sec on this hardware (3.75 vCPUs). Processing all 400 logins requires ~54 seconds; users whose login hasn't completed within the 30-second `login()` timeout hit `StopUser`. This is a test design bug — read workers do not need to authenticate individually and should share a pre-fetched token instead.

**Issue B — Instantaneous spawn rate:** `make_shape()` returns `(400, 400)` for moderate phase — all 400 users spawn within 1 second. This fires all 400 bcrypt logins simultaneously, amplifying the CPU saturation from Issue A. Capping the spawn rate alone is insufficient because the total bcrypt work (400 logins at 7.4 RPS) still exceeds the timeout budget; it only changes the failure shape, not the outcome.

Other groups (cpu_bound=100, write_ops=100, misc_lightweight=110) are unaffected — their smaller spawn counts complete within the 30s timeout window at Azure's bcrypt throughput.

**Why this did not occur on Railway (runs 3–4):** Railway was provisioned with 8 vCPUs, giving ~36 bcrypt/sec login throughput. 400 logins ÷ 36 RPS = ~11 seconds — well within the 30s timeout. The same design bug exists on Railway but is masked by the higher CPU budget. If Railway vCPUs were reduced, the same collapse would occur.

**Impact:** `read_heavy/moderate` ran at 16% of intended capacity (64 of 400 users). Actual RPS was ~12–16 per endpoint; intended was ~100. The results are not representative of 400-user moderate load.

#### 2. P95 Lower Than Average (Statistical Contamination)

For `GET /api/v1/meta` moderate: **Avg=214ms, P50=18ms, P95=21ms**.

This is statistically valid but misleading. The cumulative stats include both:
- **Steady state (64 users, ~90s):** P50=18ms, P95=21ms — clean
- **Stampede window (400 users, ~30s):** a few requests with 9,700–23,180ms response times (P99=9700ms, P99.9=21,000ms, max=23,180ms)

With 1,356 total requests, approximately 14 requests averaging ~12,000ms inflate the cumulative mean from ~18ms to ~214ms. The P95 correctly reflects the 64-user steady state; the mean is contaminated by the stampede window. This pattern repeats across all four `read_heavy/moderate` endpoints.

### Fix Plan

**Fix 1 — Pre-authenticate once, share token (addresses root cause A):**

The existing `test_start` listener in `group2_reads.py` already calls `login()` once to prefetch receipt IDs. Extend it to also store the resulting auth token in a module-level variable. `ReadUser.on_start()` then reads the shared token instead of calling `safe_login()`. This reduces login calls from 400 to 1 regardless of user count or spawn rate.

**Fix 2 — Cap spawn rate in `make_shape()` (addresses root cause B, defence-in-depth):**

The moderate branch currently sets `spawn_rate = user_count`, which fires all logins at once. Cap the spawn rate to a fixed maximum (e.g. 20 users/sec) so logins are staggered even if Fix 1 were not applied. Fix 1 alone is sufficient; Fix 2 is defence-in-depth for other groups that may grow beyond login capacity in future.
