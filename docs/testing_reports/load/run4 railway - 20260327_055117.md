## Root Cause Analysis — group1_cpu/moderate Burst Failure

**Data sources:**
- Locust stats history CSV (1-second granularity): failure rate peaked at 50.9 failures/s between t=83–88s; zero failures at t=0–73s and t=103–120s
- Honeycomb query (dataset `gatheryourdeals`, environment `test`, window 05:52:40–05:53:10 UTC): all 435 HTTP 401 spans confirmed within the 30-second burst window

**CPU is NOT saturated (service runs on 8 vCPUs):**

With 8 vCPUs and bcrypt cost 12 (~300ms CPU time per operation), Go's runtime (GOMAXPROCS=8) can run 8 bcrypt goroutines in parallel. At 100 concurrent login users the expected wall-clock throughput is ~26–36 req/s — exactly what was observed (36.45 req/s, P50=2,700ms). This is normal bcrypt throughput on 8 cores, not saturation. CPU is therefore ruled out as a cause for either error type.

**HTTP 401s are user-not-found (no bcrypt ran):**

Honeycomb spans for the 401 responses show **P50 duration = 2.44ms** — sub-DB-roundtrip speed. A wrong-password path would invoke `bcrypt.CompareHashAndPassword` (~2,700ms wall time). The 2.44ms response means `GetUserByUsername` returned `nil` (user not found) and the handler returned `ErrInvalidCredential → 401` immediately, without any bcrypt work.

**HTTP 500s are also part of the same burst:**

The 75 HTTP 500 errors (P99=3,432ms) occur in the same 30-second window. These represent requests where the handler reached the bcrypt step but then failed — likely due to the same underlying connection/infra disruption causing partial or corrupted responses downstream.

**Probable cause — transient Railway/PgBouncer infrastructure event:**

All 509 errors (434 × 401 + 75 × 500) are concentrated in a **single 30-second burst** (05:52:40–05:53:10 UTC). The service was healthy before and after. The throughput spike to 64–70 req/s during the burst (vs normal 36 req/s) is consistent with a batch of queued requests resolving instantly as fast failures, rather than completing normally at 2.7s each.

The most likely trigger is a Railway-managed PgBouncer pool health check or brief connection recycle at t≈80s, which caused `GetUserByUsername` to briefly return nil for valid usernames. This is an infrastructure variance event — the service code is correct.

**Not a code regression:**

Run 3 (GitHub run `23630392237`, same `develop` branch, same Railway environment, 90 minutes earlier) recorded **0 errors** on `cpu_bound/moderate` with identical throughput (36.1 req/s, avg 2,736ms). The code is byte-for-byte identical.

## Login Throughput Analysis

**Why is Railway login throughput lower than run 1 (local)?**

Three compounding factors explain the 93 → 36 req/s drop:

**1. bcrypt is clock-speed sensitive — cloud vCPUs are slower than local cores**

bcrypt cost-12 is pure CPU computation; throughput scales with single-core clock speed, not core count. A fast consumer CPU (3–5 GHz, dedicated) completes one bcrypt in ~100–200ms. A Railway shared vCPU completes the same operation in ~200–400ms. This alone accounts for most of the gap.

Honeycomb confirms the server-side P50 for successful logins in run 4 was **2,066ms** (the 2,700ms Locust-reported figure adds ~600ms of GitHub Actions → Railway network round-trip on top of that).

**2. Throughput is bounded by parallelism × per-op time**

With GOMAXPROCS=8 (no override set — Go reads `runtime.NumCPU()` at startup, which returns the host-reported vCPU count) and 100 concurrent users:

```
throughput = GOMAXPROCS / bcrypt_time_per_op
           = 8 / 0.222s
           ≈ 36 req/s  ← matches observed 36.45 req/s
```

The remaining ~1,844ms of the 2,066ms server-side P50 is **queue wait time** — users waiting for a free bcrypt slot. bcrypt itself takes ~222ms per operation at this utilisation level.

Run 1 (local, SQLite): faster per-core bcrypt (~100ms) + more effective parallel cores → 93 req/s.

**3. PostgreSQL network roundtrip (minor)**

`GetUserByUsername` adds ~10–20ms before bcrypt starts. SQLite is in-process at ~0ms. Small contribution.

**Is bcrypt the right approach?**

Yes — bcrypt cost 10–12 is the OWASP-recommended standard for password hashing. The intentional slowness prevents brute-force attacks by making each guess expensive. 36 req/s = 2,160 logins/minute, which is sufficient for any real-world usage since login is a low-frequency operation compared to reads/writes.

**Recommended improvement — bcrypt semaphore / worker pool**

Add a channel-based semaphore (sized to `GOMAXPROCS`) in `auth.Service.Login` to cap concurrent bcrypt operations. This does not increase throughput (still CPU-bound), but prevents goroutine pile-up, gives more predictable latency, and reduces PgBouncer connection pressure during login spikes.
