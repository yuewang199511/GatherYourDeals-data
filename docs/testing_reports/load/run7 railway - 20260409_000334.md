# Key Observations

## 1. Zero failures — consistent with run 6

Both run 6 and run 7 produced 0 HTTP errors across all groups. This confirms the service is stable on Railway under normal and stress conditions.

## 2. Login throughput further degraded — outage effect

`POST /api/v1/auth/login` at moderate achieved **18.6 RPS** (run 6: 23.75 RPS; run 4: 36.45 RPS). P50 rose from 3,400ms (run 6) to 5,300ms (run 7). Under stress, RPS dropped to 11.4 (run 6: 8.15). The P95 at stress hit 60,000ms and max reached 118,422ms. This is consistent with reduced Railway compute availability during the reported platform outage, compounding the existing bcrypt + Redis overhead. Error count remains 0.

## 3. Refresh tail latency elevated at stress — outage amplification

`POST /api/v1/auth/refresh` at stress: P50 250ms but **P95 = 2,800ms** (run 6: P50 400ms / P95 29,000ms). Interestingly, the P95 is markedly *better* than run 6 for this endpoint despite the outage. This may reflect run-to-run Redis queue variance rather than a systematic improvement.

## 4. Read-heavy group: higher throughput than run 6

At stress, read_heavy achieved **1,474.9 actual RPS** total — substantially above run 6's per-endpoint figures. P95 stayed at 940ms across all read endpoints. Write operations at stress achieved **737 actual RPS** (P95 540ms), healthy given the 1000 RPS target.

## 5. No regressions introduced by main promotion

Run 7 tests the `main` branch (PR #140 promote). All performance characteristics are in the same range as run 6 — differences are attributable to Railway infrastructure variance and the ongoing outage, not code changes.
