This article records the load testing results from run #2, recorded by Locust on Railway + PostgreSQL.

Service was deployed on Railway (1 replica, us-west2) backed by Railway-managed PostgreSQL, with OTel tracing shipped to Honeycomb.

## Root Cause Analysis — Why Stress Phases Failed

All 4 stress phases failed. Three distinct failure mechanisms cascaded across groups in sequence — each one left the server in a degraded state that made the next group's failures worse.

**1. Login retry storm — missing StopUser (cpu_bound/stress)**

Root cause: when a login timed out, the Locust user re-queued immediately instead of exiting. Failed logins kept accumulating, each holding a goroutine and DB connection, driving CPU further into saturation — which caused more timeouts, which caused more retries. A runaway loop.

Effect: throughput stuck at 8.9 req/s regardless of user count (same as moderate at 100 users). Login P50 rose from 11,000ms to 30,000ms — not because bcrypt got slower, but because the queue depth tripled. 278 HTTP 500s when the server exhausted its goroutine budget.

**2. Connection pool exhaustion — no open connection cap (read_heavy/stress, write_ops/stress)**

The app had no `SetMaxOpenConns` limit — `database/sql` defaults to unlimited. Under 2,000 concurrent users, the app blew past Railway PostgreSQL's `max_connections = 100`. Confirmed by Honeycomb traces showing DB connection wait spans spiking in lockstep with the HTTP 502/500 errors.

The result was bimodal: P50=22–24ms (requests that got a connection immediately) but P95=14,000–17,000ms (requests that queued behind the exhausted pool). Throughput was capped at ~20 req/s per endpoint regardless of how many users were pushing. Write-ops stress fared better (151 errors vs. 1,143 for reads) because the POST→DELETE cycle releases the DB connection between steps.

Fix applied in run 3: `SetMaxOpenConns(10)` / `SetMaxIdleConns(5)` with PgBouncer in session mode absorbing spikes.

**Side effects of DB exhaustion (misc_lightweight/stress)**

The residual DB stress from group 2 cascaded into group 4 as two downstream failures — not independent root causes:

- **772 HTTP 401s on `POST /auth/refresh`**: Token rotation in `RefreshAccessToken` (`jwt.go:97–100`) deletes the old token then issues a new one. Under DB stress, the delete succeeded but the new token write failed. The old token was gone; every subsequent refresh returned 401. A latent non-atomicity in the rotation logic — invisible under normal conditions.
- **119 HTTP 404s + 25 HTTP 500s on `PUT /api/v1/meta/:fieldName`**: Each user creates its meta field in `on_start`. Under DB stress, that creation failed (HTTP 500), leaving the field absent from the DB. Every subsequent PUT returned 404.

## Notable Observations

**Login throughput is CPU-bound, not concurrency-bound:**
- Moderate actual RPS: 8.6 (target: 100). Stress actual RPS: 8.9 (target: 500). Throughput was identical at both load levels — the server hit its bcrypt CPU ceiling at 100 users. Adding more users beyond that only increased queue depth and latency, not output.
- Login P50 at moderate was already 11,000ms — 14× higher than run 1 local (790ms). The entire delta is bcrypt on a remote single-replica instance vs. bcrypt on a local dev machine with no network round-trip.

**Read endpoints were effectively idle during stress:**
- Read actual RPS under stress: ~20/endpoint (target: 500). Most users were stuck waiting for logins. The "15–24ms" P50 on read endpoints is not a true latency baseline — it reflects the tiny fraction of requests that completed while the rest were queued. Run 3 reveals the real baseline is 130ms (GitHub Actions → Railway network round-trip).

**Write-ops stress was partially self-limiting:**
- POST→DELETE cycle keeps connection hold time short — 0.4% error rate vs. 40%+ on reads. This is structural: write operations release their DB connection between steps, reducing peak concurrency on the pool at any instant.
